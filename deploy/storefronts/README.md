# Storefront hosting and one-click launch

This is the hosting platform for the PHP `shop` application and the Android website launch screen. It provisions real PostgreSQL schemas and roles, storefront files, and HTTPS routing. A successful API request queues work; only a verified storefront becomes `LIVE`.

## Prepare the platform once

1. Use a Linux host with Docker Engine, Compose v2, persistent storage, and a fixed public IPv4 address. Ports 80/443 must reach Caddy. This stack owns those ports and `api.swapnopay.top` on that host. If Nginx, the Oracle stack, or another ingress already owns them, merge the routing deliberately before deployment; do not start competing stacks. The marketing website can remain on its existing host.
2. Copy `.env.example` to `.env` in this directory and fill every blank. Generate independent secrets with `openssl rand -hex 32`. `SHOP_DB_PASSWORD` must be URL-safe; use hex. `SHOP_CONFIG_KEY` must be exactly 64 hex characters and must be retained with encrypted backups. Existing platform Supabase credentials and API secrets are also required. Do not use a Supabase database as `SHOP_DATABASE_URL`: the included database is dedicated to storefront hosting and requires role/schema creation privileges.
3. Set `SHOP_SERVER_IPS` to the server's public address. Create A records for `api.swapnopay.top` and `*.shops.swapnopay.top` pointing to it. Remove conflicting AAAA records. Use DNS-only records while verifying the deployment; the verifier expects the configured origin addresses, not CDN proxy addresses. Set the certificate contact email.
4. Register each merchant's Supabase connection in the existing platform merchant registry. The app must have a valid Supabase user session. The API accepts a platform owner JWT, a registered merchant project JWT with a matching `merchants.id/user_id` ownership record, or the operator's admin secret. Public anon keys and the app's local session marker do not authorize launches. Approved self-hosted authentication domains must appear in `SHOP_AUTH_HOSTS`.
5. From the repository root, run `bash deploy/deploy-vps-shop.sh`. It validates configuration, builds Composer/Node dependencies, starts services, and checks startup health. It does not claim any storefront is live until its own verification succeeds.
6. In the Android app, open **Your online store**, enter the store name, address and admin email, then **Launch my website**. Save a generated password when shown. Custom passwords require 12 characters and at most 72 UTF-8 bytes. The status progresses through `QUEUED`, `PROVISIONING`, `WAITING_DNS`, `WAITING_TLS`, and `LIVE`. Failures show an error and support a retry. Closing the app does not stop the server job.

For a custom domain, point its A record at the displayed server address and save it. Domain claims are unique, DNS is checked before certificate authorization, and HTTPS must return the matching merchant health response. Old custom domains are removed from routing and retained as reserved claims; an operator must review ownership before releasing one to a different merchant. Store slugs remain fixed after the first launch.

## Database and files

- `swapnopay-backend/sql/storefront.sql` is the clean, version 1 storefront schema. It creates 66 legacy-compatible application tables plus login throttling, indexes, constraints and reference data. It does not import demo customers, orders, API credentials, or admin accounts. Currency is BDT and new stores offer cash on delivery.
- The worker uses `shop_control.launches` as a durable queue and `shop_control.domains` for domain reservations. Secrets are encrypted using AES-256-GCM. Each merchant receives a `store_<uuid>` schema and a separate PostgreSQL login role restricted to that schema. PHP does not receive the platform service-role key or provisioning credentials.
- Runtime credentials live under `/srv/runtime/hosts`, outside web roots. Each store has its own code copy and uploads under `/srv/shops/stores`; hostname directories are controlled symlinks. Caddy blocks configuration files, diagnostic routes, dependencies, and executable uploads. The PHP process can write uploads but not the provisioned application source.
- The legacy `supabase/SHOP_POSTGRES_SCHEMA.sql` contains demo records and shared-table policies. Four invalid defaults were repaired for reference, but it is **not** the schema used by hosting. Do not import it into a new hosted tenant. Existing shop data requires a reviewed migration and backup; the launcher deliberately does not overwrite a legacy database.
- Checkout recalculates prices and shipping, locks stock, validates coupons, inserts the order and decrements stock in one transaction. Repeated submissions of the same checkout reuse the saved order. Order receipts require the owning customer session. Browsing pages no longer expires or deletes pending orders.
- Hosted account registration creates an email/password account with delivery details; it does not claim email ownership has been verified. Optional OAuth/SMS and online payment integrations require server-side verification and configuration before enabling them. Hosted storefronts currently expose cash on delivery only; the app states this explicitly. SMTP must be configured in the admin settings for email notifications/password recovery.

## Operations and verification

Run backend tests with `cd swapnopay-backend && npm ci && npm test`. The PostgreSQL tests execute actual schema, grants, provisioning and inventory SQL using PGlite; advisory-lock concurrency still requires a real PostgreSQL server. Run `npm run test:shop-php` with `PHP_BINARY` set to a PHP 8.2+ binary with PDO PostgreSQL for HTTP checkout tests. Validate the ingress with `caddy validate --config deploy/storefronts/Caddyfile --adapter caddyfile`.

Monitor `/healthz`, launch failures, certificate renewal, storage use, and database backups. A previously live site is rechecked after 60 seconds when status is requested and becomes `DEGRADED` when HTTPS/DNS verification fails. Preserve the database, `sites`, `runtime`, Caddy storage, and `SHOP_CONFIG_KEY` together. Test restoration before accepting live orders. Never run `docker compose down -v` on production data.

Template changes apply to newly provisioned stores. Updating an existing store's code or schema requires an explicit versioned migration with a backup; changing its business settings does not overwrite uploads or customer data. The included stack uses one PHP runtime for trusted platform code, not a sandbox for merchant-supplied plugins or PHP scripts.

No server deployment, DNS changes, certificate issuance, payment-provider setup, or database migration of an existing live store is performed by editing this repository. Complete a launch and checkout on the target server before opening sales.
